# 发布与自动更新

本文说明 LiveEmail 的 Windows 打包、签名、GitHub Releases 发布与自动更新流程。

## 1. 版本与产物

| 项目 | 位置 / 说明 |
|------|-------------|
| 应用版本 | `src-tauri/tauri.conf.json` 的 `version`，同时同步 `package.json` 的 `version` |
| 安装包 | `src-tauri/target/release/bundle/nsis/LiveEmail_<version>_x64-setup.exe` |
| 更新签名 | 同目录下的 `.sig` 文件（仅在启用 `createUpdaterArtifacts` 时生成） |
| 更新清单 | `latest.json`（由 tauri-action 生成并上传） |
| 更新源 | `plugins.updater.endpoints`，当前为 `https://github.com/moreen-zsy/LiveEmail/releases/latest/download/latest.json` |
| 更新公钥 | `plugins.updater.pubkey`（已写入，可公开） |

发布前必须同时修改两处版本号，并更新 `CHANGELOG.md`：

```bash
# 示例：0.1.0 -> 0.1.1
# 1. 修改 src-tauri/tauri.conf.json: "version": "0.1.1"
# 2. 修改 package.json: "version": "0.1.1"
# 3. 更新 CHANGELOG.md
git tag v0.1.1
git push origin v0.1.1
```

## 2. 更新签名密钥

自动更新要求对安装包做 minisign 签名，客户端用内置公钥校验。**私钥严禁入库、严禁上传到仓库或制品库。**

### 2.1 生成密钥（只需一次）

```bash
bunx tauri signer generate -w ~/.liveemail/liveemail-updater.key
```

会生成：

- `liveemail-updater.key`：私钥（含密码保护）
- `liveemail-updater.key.pub`：公钥

将公钥内容（单行 Base64）填入 `src-tauri/tauri.conf.json` 的 `plugins.updater.pubkey`。当前项目已完成该配置，私钥保存在仓库外（`C:\Users\20717\.liveemail\`），请自行备份到密码管理器；丢失私钥后无法为已发布版本推送更新，只能换新公钥并让用户手动重装。

### 2.2 配置 CI Secrets

在 GitHub 仓库 Settings → Secrets and variables → Actions 中添加：

| Secret | 内容 |
|--------|------|
| `TAURI_SIGNING_PRIVATE_KEY` | 私钥文件全文（或 Base64 内容） |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | 私钥密码；无密码则留空或不配置 |

## 3. 本地构建

普通构建（不产生产品签名，适合内部验证）：

```bash
bun install
bun run test
bunx tauri build --bundles nsis
```

发布构建（生成 `.sig` 与更新产物，需要签名私钥）：

```bash
export TAURI_SIGNING_PRIVATE_KEY="$(cat ~/.liveemail/liveemail-updater.key)"
export TAURI_SIGNING_PRIVATE_KEY_PASSWORD="<密码>"
bunx tauri build --bundles nsis --config src-tauri/tauri.release.conf.json
```

`src-tauri/tauri.release.conf.json` 只追加：

```json
{ "bundle": { "createUpdaterArtifacts": true } }
```

日常本地构建不加载该配置，因此不需要签名环境变量。

## 4. CI 发布流程

工作流文件：`.github/workflows/release.yml`，由 `v*` 标签触发。

1. 检出代码，安装 Bun 与 Rust 稳定版工具链。
2. 运行 Rust 单元测试与前端 Vitest。
3. 调用 `tauri-apps/tauri-action` 构建 NSIS 安装包，使用签名 Secrets 生成 `.sig`。
4. 创建 **Draft Release**，上传安装包、`.sig` 和 `latest.json`。
5. 人工在 GitHub 上检查产物后点击 Publish。

发布后，`https://github.com/moreen-zsy/LiveEmail/releases/latest/download/latest.json` 即可被客户端访问。

### 4.1 latest.json 格式

tauri-action 生成的内容大致如下（字段由插件定义，不要手工改写格式）：

```json
{
  "version": "0.1.1",
  "pub_date": "2026-11-20T08:00:00Z",
  "notes": "修复若干问题",
  "platforms": {
    "windows-x86_64": {
      "signature": "<.sig 文件内容>",
      "url": "https://github.com/moreen-zsy/LiveEmail/releases/download/v0.1.1/LiveEmail_0.1.1_x64-setup.exe"
    }
  }
}
```

客户端行为：设置页「检查更新」→ 发现新版本 → 用户确认 → 下载并校验签名 → 静默/被动模式安装 → 重启应用。

## 5. 更新发布检查

1. 旧版本（如 0.1.0）已安装并能正常启动。
2. 新版本 `latest.json` 中 `version` 高于旧版本。
3. 设置页检查更新能弹出新版本号。
4. 更新完成后版本号变化，账户、邮件、草稿等用户数据保留。
5. 断开网络或签名不匹配时，更新应失败并给出提示，不得覆盖用户数据。

## 6. 回滚

- 已发布版本无法“降级推送”。如需回滚，重新发布一个版本号更高、内容为旧功能的版本。
- GitHub Release 的 `latest` 指向最新非预发布版本；不要把有问题的草稿直接 Publish。
- 数据库迁移只增不减，回滚版本需兼容更高版本已写入的 schema（当前迁移均向后兼容，见 `src-tauri/src/db/mod.rs`）。

## 7. 常见问题

| 现象 | 处理 |
|------|------|
| 构建报缺少签名环境变量 | 本地不加 `--config src-tauri/tauri.release.conf.json`；CI 检查 Secrets |
| 客户端提示签名验证失败 | 公钥与签名私钥不匹配，确认 `pubkey` 对应本次签名密钥 |
| 检查更新 404 | `latest.json` 未上传，或 endpoint 指向的仓库/标签不正确 |
| 更新后打不开 | 检查 NSIS 安装模式（currentUser）与杀软拦截；查看 `%LOCALAPPDATA%\com.liveemail.app` 日志 |
